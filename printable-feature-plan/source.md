| 항목 | 내용 |
|---|---|
| 문서 상태 | 기획 초안 — 구현·배포 대상 아님 |

| 목적 | 향후 개발 의사결정과 요구사항 정리를 위한 기준 문서 |

> **핵심 방향:** “사업의 끝, 시작의 가치.” 클로징마켓은 일반 개인 간 중고거래 서비스가 아니라, 폐업·이전·물품 교체·업종 변경·매장 정리·사업장 확장 또는 축소 과정에서 발생하는 **사업장 물품**과 사업 관련 서비스를 연결하는 플랫폼을 지향한다.

## 1. 문서의 범위와 원칙

이 문서는 사용자 제공 요구사항을 바탕으로, 현재 운영 중인 서비스와 향후 후보 기능을 분리해 정리한 개발 참고용 문서다. 아래 기능은 승인된 개발 백로그가 아니라, 실제 이용자·판매자·업체 수와 거래 데이터를 확인한 뒤 우선순위를 정할 수 있는 **기획 초안**이다. 따라서 이 문서만으로 앱 기능, API, 데이터 모델 또는 과금 정책이 자동 변경되지는 않는다.

서비스의 모든 확장 기능은 사업장 물품과 사업 관련 서비스라는 정체성을 유지해야 한다. 일반 개인의 일상 중고거래 수요를 광범위하게 수용하기보다는, 사업자 인증·사업장 상황·물품 용도·전문 업체 연결을 통해 거래 맥락이 분명한 구조를 우선한다.

## 2. 현재 서비스와 향후 기능의 구분

| 구분 | 현재 운영 또는 출시 범위 | 향후 개발 후보 범위 |
|---|---|---|
| 물품 거래 | 사업자 인증 기반 판매자의 물품 등록, 물품 탐색, 지역·카테고리 기반 조회, 채팅, 찜, 후기 | 구매자가 필요한 물품을 먼저 등록하는 **찾아요** 수요 게시판 |
| 판매 상황 | 폐업물품 중심의 물품 등록 흐름 | 폐업 외 사업장 이전, 물품 교체, 업종 변경, 매장 정리, 확장·축소 상황을 구조적으로 분류 |
| 업체 연결 | 업체 정보 탐색 및 문의 연결 | 통합찾기, 업체 카테고리 고도화, 견적 요청, 방문 예약, 리드 연결 관리 |
| 수익화 | 초기 이용자·물품·업체 확보를 우선 | 업체 리드 연결비, 광고, 상위 노출, 구독, 안전결제 및 부가 서비스 수수료 검토 |
| 개인정보 | 기존 계정·물품·채팅 운영 범위 | 주소·연락처 단계 공개, 안심번호, 견적·방문 데이터 보관 정책 설계 |

현재 출시본에는 통합찾기, 견적 요청, 방문예약, 연결 과금 기능이 포함되지 않는다. 향후 기능을 구현할 때에는 현재의 물품 등록·검색·채팅 흐름을 해치지 않고, 출시 전 별도 기획·개발·테스트·정책 검토를 거쳐야 한다.

## 3. 공통 제품 원칙과 역할 정의

### 3.1 제품 원칙

첫째, 모든 기능은 **사업장 물품 또는 사업 관련 서비스**라는 목적에 연결되어야 한다. 둘째, 초기에는 거래와 연결을 쉽게 만들되, 주소와 연락처처럼 민감한 정보는 필요한 시점에만 제한적으로 공개한다. 셋째, 수익화 기능은 거래와 상담 수요가 충분히 검증된 이후 도입하며, 초기 물품 등록은 가능한 한 무료 정책을 유지한다.

### 3.2 공통 역할

| 역할 | 기본 권한 | 향후 확장 기능에서의 역할 |
|---|---|---|
| 일반 사용자·구매자 | 물품 탐색, 찜, 채팅, 후기 | 찾어요 등록, 견적 요청, 방문 예약 요청 |
| 인증 판매자 | 물품 등록, 수정·삭제, 구매자 채팅 | 찾어요 게시글 탐색, 관심 수요에 제안 또는 채팅 연결 |
| 인증 업체 | 업체 정보 등록 및 고객 문의 확인 | 견적 요청 조회, 상담·방문 제안, 예약 승인, 유료 리드 연결 신청 |
| 관리자 | 회원·물품·업체·신고 관리 | 수요·견적·예약 신고 처리, 카테고리 운영, 정책 위반 검토, 과금 분쟁 관리 |

### 3.3 공통 상태 원칙

향후 요청형 기능에는 상태값이 명확해야 한다. 사용자는 요청이 접수되었는지, 업체 또는 판매자가 읽었는지, 채팅으로 연결되었는지, 거래·상담·방문이 종료되었는지 알 수 있어야 한다. 상태 변경은 알림과 연결하되, 불필요한 광고성 알림은 사용자가 설정에서 제어할 수 있게 설계한다.

## 4. 기능 A — 찾아요

### 4.1 기능 정의와 목적

**찾아요**는 구매자가 필요한 사업장 물품을 직접 등록하고, 인증 판매자가 해당 수요를 발견해 연락할 수 있게 하는 양방향 거래 기능이다. 현재의 “판매자가 물건을 등록하고 구매자가 검색하는 구조”를 보완해, “구매자가 원하는 물건을 등록하고 판매자가 구매 수요를 발견하는 구조”를 만든다.

이 기능은 초기 이용자가 충분히 확보되고 실제 구매 수요가 확인된 이후에 개발한다. 물품 공급과 수요가 적은 초기 단계에서 먼저 도입하면 비어 있는 요청 게시판이 서비스 신뢰를 낮출 수 있기 때문이다.

### 4.2 대표 사용자 시나리오

| 시나리오 | 흐름 | 사용자 가치 |
|---|---|---|
| 카페 창업 준비 | 구매자가 “부산 카페 테이블 10개”를 조건과 함께 등록 → 판매자가 확인 → 채팅 연결 → 거래 완료 표시 | 검색만으로 찾기 어려운 다수·특정 수량의 물품 수요를 알릴 수 있음 |
| PC방 장비 교체 | 운영자가 “모니터 30대”를 예산·상태·희망일과 함께 등록 → 여러 판매자가 관심 표시 또는 연락 | 대량 구매 조건을 한 번에 전달할 수 있음 |
| 폐업 재고 활용 | 판매자가 유사 수요 게시글을 보고 보유 물품을 제안 → 구매자와 채팅 | 이미 보유한 사업장 물품의 구매자를 능동적으로 찾을 수 있음 |

### 4.3 주요 화면과 입력값

| 화면 | 목적 | 주요 입력 또는 표시 항목 |
|---|---|---|
| 찾아요 목록 | 현재 수요 탐색 | 물품명, 카테고리, 지역, 수량, 예산 범위, 희망 거래일, 상태, 등록일 |
| 찾아요 등록 | 구매 수요 작성 | 찾는 물품명, 카테고리, 지역, 희망 가격·예산, 수량, 원하는 상태, 희망 거래일, 상세 설명, 사진 |
| 찾아요 상세 | 수요 조건 확인과 판매자 연결 | 전체 요청 내용, 작성자 기본 정보, 관심 수, 상태, 신고, 채팅 또는 제안 진입 |
| 내 요청 관리 | 등록한 요청 관리 | 수정, 삭제, 거래 진행·완료 상태 변경, 관심 또는 연락 현황 |
| 판매자 탐색 화면 | 판매자가 수요를 필터링 | 카테고리·지역·예산·수량·거래일 필터, 저장 검색 |

### 4.4 주요 동작과 상태

요청은 `모집 중`, `거래 협의 중`, `거래 완료`, `마감`, `삭제` 상태로 관리한다. 구매자는 모집 중인 요청만 수정할 수 있고, 거래가 끝나면 거래 완료 또는 마감 처리한다. 판매자는 요청의 조건을 확인한 뒤 채팅을 시작할 수 있으며, 요청 내용과 무관한 홍보성 메시지는 신고·제한 대상이 된다.

초기 버전에서는 별도의 견적 제안서 기능보다 기존 채팅 시스템을 우선 재사용하는 것이 적절하다. 거래 수요가 충분해지면 판매자의 보유 수량·예상 가격·운송 가능 여부를 구조화한 제안 카드 기능을 검토할 수 있다.

### 4.5 권한·알림·결제·개인정보

| 항목 | 기획 원칙 |
|---|---|
| 등록 권한 | 로그인한 일반 사용자와 인증 회원이 등록 가능하되, 스팸 방지를 위한 등록 빈도 제한을 검토 |
| 열람 권한 | 기본 조건은 공개하되, 작성자의 정확한 연락처·상세 주소는 공개하지 않음 |
| 채팅 권한 | 인증 판매자 또는 운영 정책상 허용된 회원이 요청자에게 채팅 연결 가능 |
| 알림 | 관심 조건과 유사한 신규 요청, 새 채팅, 상태 변경, 마감 예정 알림 |
| 결제 여부 | 초기에는 없음. 거래 자체의 결제·수수료는 별도 안전결제 정책 수립 전까지 도입하지 않음 |
| 개인정보 주의사항 | 상세 주소·전화번호·사업자 식별정보를 게시글 본문에 직접 입력하지 못하도록 안내·필터링 검토 |

### 4.6 현재 개발하지 않는 이유와 추후 고려사항

현재는 물품 공급과 실제 거래 흐름을 먼저 안정화해야 한다. 추후 개발 시에는 요청의 유효 기간, 중복·허위 수요, 다수 판매자의 과도한 연락, 대량 구매의 가격 협상, 사진 속 개인정보 노출, 거래 실패 시 후기·신고 기준을 먼저 설계해야 한다.

## 5. 기능 B — 통합찾기

### 5.1 기능 정의와 목적

**통합찾기**는 사업을 시작하거나 종료·이전·정리하는 사용자가 자신의 상황을 입력하면, 필요한 물품 거래와 관련 전문 서비스를 한 흐름으로 탐색하도록 돕는 기능이다. 단순한 업체 목록이 아니라, 사용자의 사업장 상황을 기준으로 필요한 다음 행동을 안내하는 구조를 목표로 한다.

예를 들어 “카페 폐업 예정”을 선택한 사용자는 물품 판매, 철거, 폐기물 처리, 청소, 원상복구, 운송 순서의 관련 서비스를 확인할 수 있다. “사업장 이전”을 선택한 사용자는 기존 물품 정리, 운송, 신규 공간 인테리어, 추가 장비 구매 등을 안내받는다.

### 5.2 대표 사용자 시나리오

| 상황 | 입력 예시 | 연결 후보 |
|---|---|---|
| 폐업 | 카페 폐업 예정, 30평, 부산 남구 | 물품 판매, 철거, 폐기물, 청소, 원상복구, 운송 |
| 사업장 이전 | 사무실 이전, 기존 가구 일부 처분 | 중고 집기 판매, 운송, 새 공간 인테리어, 신규 장비 |
| 물품 교체 | PC방 모니터 교체, 기존 장비 처분 | 기존 장비 판매, 중고 장비 탐색, 운송·설치 업체 |
| 신규 창업 | 음식점 창업 준비 | 업소용 중고 집기 탐색, 인테리어, 간판, 설비, 운송 |

### 5.3 주요 화면과 입력값

| 화면 | 목적 | 주요 입력 또는 표시 항목 |
|---|---|---|
| 상황 선택 | 사용자의 목적 분류 | 폐업, 이전, 물품 교체, 업종 변경, 매장 정리, 확장·축소, 신규 창업 |
| 기본 정보 입력 | 맞춤 연결 조건 수집 | 사업장 종류, 지역, 평수 또는 규모, 희망 일정, 필요한 서비스, 사진, 상세 상황 |
| 통합 결과 | 단계별 필요 항목 안내 | 우선 행동, 물품 거래 링크, 업체 카테고리, 견적 요청 진입, 저장한 계획 |
| 진행 관리 | 사용자가 선택한 항목 관리 | 완료·보류 상태, 채팅·견적·방문 예약 현황, 알림 |

### 5.4 주요 동작과 권한

초기 통합찾기는 **추천·탐색 도우미**로 시작하고, 견적·예약·과금은 별도 기능이 준비된 뒤 연결한다. 입력 내용은 사용자가 직접 저장 또는 요청 제출하기 전까지 외부 업체에 공개하지 않는다. 사용자는 자신의 상황을 저장·수정·삭제할 수 있으며, 업체는 직접 식별 가능한 정보 없이 카테고리별 수요 경향만 볼 수 있도록 향후 설계할 수 있다.

### 5.5 알림·결제·개인정보

통합찾기 자체는 무료 안내 기능으로 두고, 견적 요청·방문 예약 등 후속 행위에서만 단계별 알림을 제공한다. 사업장 위치는 시·군·구 수준의 대략 정보부터 활용하며, 정확한 주소와 연락처는 사용자가 특정 업체와 연결을 승인한 뒤에만 공개한다. 사진에 사업장 명칭, 전화번호, 주소가 노출될 수 있으므로 업로드 전 안내와 자동 검토 절차를 검토한다.

### 5.6 현재 개발하지 않는 이유와 추후 고려사항

통합찾기는 여러 기능을 묶는 허브 성격이므로, 물품 거래·업체 데이터·견적·예약 흐름이 분리된 상태에서 먼저 출시하면 빈 화면이나 끊긴 흐름을 만들 수 있다. 각 카테고리의 실제 업체 공급과 고객 수요가 확보된 뒤, 최소 기능부터 단계적으로 도입해야 한다.

## 6. 기능 C — 업체찾기 고도화

### 6.1 기능 정의와 목적

업체찾기 고도화는 현재의 업체 정보 탐색을, 카테고리별 비교·상담·견적·방문 연결이 가능한 서비스 탐색 흐름으로 발전시키는 기능이다. 업체의 존재를 보여주는 데서 그치지 않고, 사용자가 자신의 사업장 상황에 적합한 업체를 찾고 다음 행동을 시작할 수 있게 한다.

### 6.2 주요 카테고리와 화면

| 영역 | 우선 카테고리 예시 | 고도화 방향 |
|---|---|---|
| 철거·정리 | 철거, 폐기물 처리, 청소, 원상복구 | 지역·사업장 규모·희망 일정으로 탐색 및 견적 요청 연결 |
| 이전·운송 | 운송, 이사, 보관, 설치 | 운송 물량·층수·엘리베이터 여부·희망일 기반 상담 |
| 공간·시설 | 인테리어, 간판, 현수막, 설비 | 업종·예산·면적·시공 범위 기반 상담 |
| 장비·물품 | 중고기기, 주방기기, POS·키오스크, CCTV·보안 | 물품 탐색과 업체 서비스 연결 |
| 사업 지원 | 부동산, 창업 컨설팅, 세무·노무 | 사업 시작·종료 단계별 유의사항과 상담 연결 |

업체 상세 화면에는 기본 업체 정보, 제공 서비스, 서비스 지역, 상담 가능 시간, 소개 사진, 후기, 견적 요청 버튼, 방문 상담 가능 여부를 단계적으로 추가할 수 있다. 비교·순위 표시는 광고 여부와 일반 노출 여부를 명확하게 구분해야 한다.

### 6.3 권한·알림·결제·개인정보

인증 업체만 업체 프로필과 견적 응답 권한을 갖도록 한다. 사용자는 업체를 찜하거나 견적 요청을 시작할 수 있으며, 새 응답·상담 메시지·예약 변동에 대한 알림을 받는다. 초기 업체 등록과 기본 노출은 무료를 우선 검토하고, 유료 상위 노출이나 광고는 일반 검색 결과와 명확히 구분한다. 후기 조작, 허위 자격, 과장 광고, 무단 연락을 방지할 운영 기준이 필요하다.

### 6.4 현재 개발하지 않는 이유와 추후 고려사항

업체 정보의 정확성과 응답률이 확보되지 않으면 고도화된 탐색 화면이 실질적인 가치를 만들기 어렵다. 먼저 실제 업체 회원의 업종·지역·서비스 범위를 정비하고, 사용자의 검색·문의 데이터를 통해 우선 카테고리를 선정하는 것이 적절하다.

## 7. 기능 D — 견적 요청

### 7.1 기능 정의와 목적

**견적 요청**은 사용자가 선택한 업체 또는 카테고리에 자신의 사업장 상황을 전달하고, 업체가 견적 또는 방문 상담 의사를 응답하도록 하는 기능이다. 이는 단순 채팅보다 구조화된 상담 정보를 제공해 업체와 고객 모두의 반복 확인 비용을 줄이는 것을 목적으로 한다.

### 7.2 주요 화면과 입력값

| 화면 | 목적 | 입력 또는 표시 항목 |
|---|---|---|
| 견적 요청 작성 | 상담 조건 입력 | 견적 요청 사유, 사업장 종류, 지역, 평수, 상세 내용, 희망 일정, 사진, 추가 요청사항 |
| 요청 상세 | 요청 내용·응답 확인 | 상태, 업체 응답, 문의 이력, 사진, 수정·취소, 신고 |
| 업체 요청함 | 업체가 수신한 요청 관리 | 대략 지역, 업종, 면적, 요청 내용, 희망 일정, 사진, 연결 가능 상태 |
| 응답 작성 | 업체의 상담 의사 표시 | 견적 범위 또는 상담 제안, 방문 가능 여부, 메시지, 유효 기간 |

### 7.3 주요 동작과 상태

견적 요청은 `작성 중`, `접수`, `업체 확인`, `상담 제안`, `방문 조율`, `완료`, `취소`, `만료` 상태를 기본으로 한다. 사용자는 접수 전에는 자유롭게 수정할 수 있고, 접수 후에는 중요한 변경 사항을 이력으로 남긴다. 업체는 요청을 읽은 뒤 상담 가능 여부를 응답하며, 가격을 확정 약속하는 문구와 참고 견적 범위를 구분해 표시해야 한다.

### 7.4 권한·알림·결제·개인정보

| 항목 | 기획 원칙 |
|---|---|
| 요청 권한 | 로그인한 사용자가 요청 가능. 반복·허위 요청 방지를 위한 제한 검토 |
| 열람 권한 | 인증된 업체 중 해당 카테고리·지역 조건을 충족하는 업체 또는 사용자가 선택한 업체 |
| 알림 | 접수, 업체 열람, 응답, 채팅 연결, 만료·취소, 예약 상태 변경 |
| 결제 여부 | 고객의 견적 요청은 초기 무료. 업체의 상세 연락처 공개 또는 리드 연결 시 과금 여부는 별도 기능 F에서 결정 |
| 개인정보 | 초기는 시·군·구 수준 지역과 요청 조건만 제공하고, 정확한 주소·전화번호는 단계적 공개 원칙 적용 |

### 7.5 현재 개발하지 않는 이유와 추후 고려사항

견적 요청은 수요와 공급이 모두 있는 카테고리부터 시작해야 한다. 업체 응답이 늦거나 없는 요청이 누적되면 고객 경험이 나빠질 수 있으므로, 카테고리별 최소 업체 수·평균 응답률·운영 인력 기준을 정의한 뒤 도입한다. 견적 분쟁, 허위 견적, 시공 품질 보증 범위, 플랫폼 책임 한계도 정책 문서와 함께 정리해야 한다.

## 8. 기능 E — 방문예약

### 8.1 기능 정의와 목적

**방문예약**은 견적 요청 이후 사용자와 업체가 실제 사업장 방문 일정을 요청·승인·변경·취소하는 기능이다. 채팅에서 날짜를 반복 조율하는 과정을 줄이고, 방문 일정과 상태를 양쪽이 동일하게 확인하도록 돕는다.

### 8.2 대표 사용자 시나리오

사용자는 “9월 28일 오후 방문 희망”을 선택해 방문 요청을 보낸다. 업체는 가능 시간을 제안하거나 “9월 28일 오후 3시 가능”으로 승인한다. 양측이 확정하면 예약 상태가 확정으로 변경되고, 방문 전 알림이 발송된다.

### 8.3 주요 화면과 입력값

| 화면 | 목적 | 입력 또는 표시 항목 |
|---|---|---|
| 방문 요청 | 가능한 일정 제안 | 희망 날짜, 시간대, 방문 목적, 현장 유의사항, 추가 메모 |
| 업체 일정 응답 | 승인·대안 일정 제안 | 가능 날짜·시간, 응답 메시지, 방문 가능 인원 또는 조건 |
| 예약 상세 | 확정 일정 관리 | 예약 상태, 양측 메모, 변경·취소 사유, 알림 설정 |
| 내 예약 목록 | 예정·완료 방문 관리 | 날짜, 업체 또는 고객, 상태, 견적 요청 연결, 채팅 진입 |

### 8.4 주요 동작과 상태

예약 상태는 `요청`, `대안 제안`, `확정`, `변경 요청`, `취소`, `방문 완료`, `미방문`으로 관리한다. 일정 변경에는 상대방의 재승인이 필요하며, 방문 완료 처리는 양측 확인 또는 운영 정책에 따른 시간 경과 처리 방식을 검토한다. 일정 확정 전에는 정확한 주소를 노출하지 않는 구조를 우선한다.

### 8.5 알림·결제·개인정보

예약 요청·승인·변경·취소·방문 전 알림을 제공한다. 초기에는 예약 자체의 결제를 도입하지 않으며, 방문비·출장비 등은 업체가 사용자와 사전에 고지하고 앱 밖 거래 조건으로 협의하도록 한다. 주소 공개는 확정된 예약 또는 사용자의 명시적 연결 동의 이후에만 가능하게 하고, 정확한 위치 정보의 보관 기간과 접근 이력을 관리해야 한다.

### 8.6 현재 개발하지 않는 이유와 추후 고려사항

방문예약은 견적 요청과 업체 응답이 안정된 뒤에만 의미가 있다. 노쇼, 방문 지연, 예약 취소, 출장비 분쟁, 업체 다중 일정 관리, 운영자 개입 기준을 함께 설계해야 한다. 초기에는 채팅 기반 일정 조율의 사용 패턴을 관찰한 뒤 필요한 카테고리에 한정해 출시하는 방식을 권장한다.

## 9. 기능 F — 주소·연락처 단계 공개 및 연결 과금

### 9.1 기능 정의와 목적

이 기능은 업체가 모든 고객 정보를 무료로 열람하지 않도록 하고, 실제 상담 또는 현장 방문 의사가 있는 경우에만 정확한 주소·연락처 또는 안심번호로 연결되는 구조다. 고객은 불필요한 영업 연락을 줄이고, 업체는 실제 가능성이 높은 리드에 집중할 수 있다.

### 9.2 단계별 공개 구조

| 단계 | 업체가 볼 수 있는 정보 | 고객 정보 보호 원칙 |
|---|---|---|
| 요청 탐색 | 시·군·구, 사업장 유형, 평수, 요청 유형, 사진, 희망 일정 | 정확한 주소·전화번호·상호명 비공개 |
| 연결 요청 | 업체의 기본 정보, 방문·상담 의사, 안내 메시지 | 고객이 업체를 선택·수락할 수 있음 |
| 연결 승인 또는 과금 완료 | 정확한 주소 또는 안심번호, 필요한 추가 정보 | 목적 외 사용 금지, 접근 이력 기록, 보관 기간 관리 |
| 예약 확정 | 현장 방문을 위한 최소 정보 | 방문 종료 후 정보 접근 범위·기간 제한 검토 |

### 9.3 결제와 수익모델

이 기능은 초기에는 무료 연결 또는 제한된 체험으로 운영 패턴을 검증한다. 이후 실제 방문·상담 전환율, 고객 만족도, 업체의 리드 가치가 확인되면 업체에 한해 `방문 요청`, `연결 요청`, `상세 연락처 공개` 단계의 연결비 또는 크레딧 모델을 검토한다. 고객에게 주소 공개를 강요하거나, 결제하지 않은 업체에 차별적 정보 접근을 제공해서는 안 된다.

### 9.4 개인정보 관련 주의사항

정확한 주소와 연락처는 개인정보 처리 목적, 제공 대상, 보유 기간, 철회 방법을 분명히 고지해야 한다. 업체가 정보를 열람한 시점과 목적을 기록하고, 무단 영업·재판매·외부 활용을 금지하는 약관과 제재 기준을 마련해야 한다. 안심번호, 주소 일부 마스킹, 최소 공개, 동의 이력, 신고·차단 기능을 우선 검토한다.

### 9.5 현재 개발하지 않는 이유와 추후 고려사항

연결 과금은 고객과 업체의 신뢰가 확보된 이후에 도입해야 한다. 수요가 부족한 상태에서 과금부터 시작하면 업체 이탈을 유발할 수 있고, 리드 품질이 낮으면 환불·분쟁 운영 비용이 커질 수 있다. 따라서 먼저 무료 연결의 응답률·방문 전환률·거래 만족도를 측정한 뒤 가격과 환불 기준을 결정한다.

## 10. 수익모델 검토 방향

초기 단계의 최우선 목표는 이용자, 판매자, 사업장 물품, 구매자, 실제 거래의 확보이다. 폐업·이전·교체·정리 과정에서 나오는 사업장 물품의 등록은 가능하면 무료 정책을 유지해 공급을 늘린다. 수익화는 거래와 상담의 가치를 검증한 뒤 투명한 고지와 선택권을 전제로 도입한다.

| 영역 | 후보 모델 | 도입 전 확인할 지표 | 유의사항 |
|---|---|---|---|
| 업체 연결 | 견적·방문 리드 연결비 | 업체 응답률, 방문 전환율, 고객 만족도 | 리드 품질·환불·개인정보 공개 기준 필요 |
| 업체 노출 | 광고, 상위 노출, 카테고리 스폰서 | 검색량, 문의량, 일반 노출 대비 효율 | 광고·추천 표기를 명확히 구분 |
| 업체 서비스 | 구독, 운영 도구, 리드 관리 | 재방문율, 업체 유지율 | 기본 탐색 기능을 과도하게 제한하지 않음 |
| 거래 | 안전결제 수수료, 운송·설치 부가 서비스 | 거래 완료율, 분쟁률, 결제 전환율 | 결제·정산·분쟁·소비자 보호 설계가 선행되어야 함 |
| 사업 양도·양수 | 중개 또는 프리미엄 서비스 | 유효 매물 수, 상담 전환율 | 법률·중개·광고 표현의 검토 필요 |

## 11. 장기 확장 시나리오

클로징마켓의 장기 방향은 “사업을 시작하거나 끝낼 때 필요한 것을 한 곳에서 해결하는 플랫폼”이다. 다만 각 시나리오는 한 번에 제공하지 않고, 실제 이용 데이터에 따라 단계적으로 연결한다.

| 상황 | 단계별 연결 예시 |
|---|---|
| 사업 시작 | 사업장 찾기 → 업소용 중고 장비 탐색 → 인테리어 → 간판 → 집기 → 운송 |
| 사업 종료 | 물품 판매 → 철거 → 폐기물 처리 → 청소 → 원상복구 → 운송 |
| 사업 이전 | 기존 물품 정리 → 새 사업장 준비 → 운송 → 인테리어 → 신규 장비 보강 |
| 물품 교체 | 기존 장비 판매 → 대체 중고 장비 탐색 → 운송·설치 → 폐기·정리 |

## 12. 개발 우선순위와 단계별 진입 기준

기능을 한꺼번에 구현하지 않는다. 현재는 이용자 확보, 인증 판매자 확보, 사업장 물품 확보, 구매자 확보, 실제 거래 확인이 선행되어야 한다. 이후에는 아래 순서를 기본 가설로 사용하되, 실제 사용 데이터에 따라 바꿀 수 있다.

## 14. 결론

클로징마켓의 다음 단계는 새로운 기능 수를 빠르게 늘리는 일이 아니라, 사업장 물품 거래의 공급과 수요를 안정적으로 연결하는 것이다. **찾아요**는 양방향 거래 구조를 만들고, **통합찾기·업체찾기 고도화·견적 요청·방문예약**은 사업장 정리와 시작에 필요한 서비스를 연결한다. **주소·연락처 단계 공개와 연결 과금**은 신뢰·수요·운영 체계가 검증된 뒤에만 도입한다.

본 문서는 향후 개발의 참고 기준으로 보관한다. 실제 구현을 시작할 때에는 대상 기능 하나를 선택해 별도 요구사항, 화면 설계, 데이터 구조, 운영 정책, 개인정보 처리, 테스트 계획, 출시 기준을 새 문서로 구체화한다.
